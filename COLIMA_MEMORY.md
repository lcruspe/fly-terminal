# Colima: возврат неиспользуемой памяти в macOS

## Статус

2026-11-27: установлен Krunkit 1.3.2 / libkrun 1.19.8, подтверждён возврат памяти на отдельной VM. Выполнена попытка переключения production с офлайн-резервной копией и автоматическим откатом. Откат на VZ выполнен из-за воспроизведённого дефекта монтирования persistent data disk (#1614); все данные и сервисы проверены. Lima и Colima не обновлялись.

- Mac mini Apple Silicon, macOS 26.7, 16 GiB RAM.
- Colima 0.10.2 / Lima 2.1.2: Docker, VZ, 4 CPU, 6 GiB RAM, 100 GiB data disk, VirtioFS.
- На момент диагностики macOS использовала около 10.5 GiB swap; в Linux доступно около 2.3 GiB из 5.8 GiB. Основной потребитель внутри VM — fallback Chromium (~3.1 GiB). Эти снимки не доказывают, что весь swap вызван Colima.
- Colima хранится на внешнем SSD, data disk занимает около 34 GiB физически. Свободное место на SSD позволяет сделать отдельную резервную копию после остановки VM.
- Установленная Lima содержит драйвер krunkit; Krunkit и libkrun установлены через Homebrew без обновления Lima и Colima. Поддержка Free Page Reporting подтверждена в отдельной VM и контрольным замером.
- Tailscale находится в независимой Lima VM; её конфигурацию, процесс и сеть не менять. Amnezia не отключать.

## Выбор технологии

VZ не гарантирует возврат страниц Linux в общее распоряжение macOS. Krunkit/libkrun >= 1.19.0 реализует free page reporting, но драйвер Lima остаётся экспериментальным. Фиксированный параметр memory остаётся верхней границей гостя; освобождаемые страницы могут повторно использоваться хостом.

## Результаты изолированного теста (27.11.2026)

- Создана согласованная офлайн APFS-копия рабочего профиля на внешнем SSD; проверены логические размеры дисков 100 GiB и 20 GiB. Сокеты runtime не копировались (они создаются заново).
- Использован отдельный профиль `k`, 2 CPU / 2 GiB RAM, без монтирования каталога хоста. Длинное имя профиля не подходит из-за ограничения UNIX_PATH_MAX=104 при хранении Colima на внешнем SSD.
- Lima 2.1.2 по умолчанию попыталась использовать SSH over vsock; Linux загрузился, но соединение последовательно закрывалось. Штатная настройка `ssh.overVsock: false` (для этого тестового экземпляра через `limactl edit --set '.ssh.overVsock=false'`) устранила проблему. Lima 2.1.3 уже отключает SSH over vsock для Krunkit по умолчанию: https://github.com/lima-vm/lima/releases/tag/v2.1.3 .
- После прерванного запуска Krunkit диск тестового экземпляра остался заблокирован. После проверки статуса Stopped и отсутствия активного процесса выполнено `limactl disk unlock colima-k`. Не применять к рабочему/работающему диску.

## Попытка переключения production (27.11.2026, 10:35–10:39 МСК)

1. Снята свежая согласованная офлайн APFS clone-копия профиля (на внешнем SSD; каталог `fly-terminal-live-vz-cutover-20261127-103457`). Сверены размер root disk 20 GiB и data disk 100 GiB. Сохранён инвентарь 6 контейнеров, 2 volumes, всех образов и параметры монтирования активных контейнеров.
2. Выполнен штатный soft-delete системной VM без флага `--data`. Data disk сохранился. Восстановленная конфигурация отличается только vmType=krunkit и отдельным Colima/Lima override `ssh.overVsock: false`. Запуск через прежний Homebrew launch agent.
3. Krunkit и Docker запустились, но инвентарь Docker оказался пустым. Раздел ext4 с меткой `lima-colima` был обнаружен гостем как /dev/vdc1, однако не был смонтирован. Docker/Containerd получили bind mount с root filesystem (/dev/vda1) вместо сохранённого data disk. Cloud-init завершился с ошибкой, включая `resize2fs: Please run 'e2fsck -f ...' first`.
4. Это совпадает с открытым upstream-дефектом **abiosoft/colima#1614**: https://github.com/abiosoft/colima/issues/1614 . Проблема воспроизводится и при stop/start, поэтому одноразовое ручное исправление mount/fsck не является надёжным решением для постоянного сервера. Не применять fsck к рабочему data disk, не выполнять hard delete и не переводить production на данный стек до подтверждённого исправления.
5. Автоматический rollback: остановлен Krunkit, его root/data/config сохранены отдельно в `fly-terminal-live-krunkit-failed-20261127-103457`; исходные VZ root/data/config восстановлены из APFS копии, временный override удалён. Запущен исходный Homebrew service.
6. Проверки после rollback: профиль default=VZ Running; Docker context colima; все 6 контейнеров, 2 volumes и IDs образов совпадают с инвентарём; /dev/vdb1 корректно mounted в /mnt/lima-colima, /var/lib/docker на том же ext4, 17 GiB данных. Chromium HTTP 7690=200, Quasar HTTPS 8443=404 (исходный ответ), bind mounts доступны. Gateway HTTPS=200. PID отдельных Tailscale/Amnezia процессов сохранились. Pilot остановлен; backup не удалён.

**Решение:** VZ остаётся рабочим backend. Krunkit показал желаемый возврат памяти, но в текущей комбинации версий непригоден для production с постоянным data disk. Следующая попытка только после исправления #1614 либо отдельного воспроизводимого теста официального исправления с сохранённым диском, несколькими штатными перезапусками и проверкой всей цепочки до Docker. При разработке исправления использовать исключительно копию диска, не рабочий диск.

### Уточнение причины (27.11.2026)

В исходном коде Colima v0.10.2, `environment/vm/lima/disk.sh`, при проверке диска оба вызова `findmnt` используют `--target "$MOUNT_POINT"`. Это ищет файловую систему, содержащую путь, а не только точку монтирования. Если каталог уже создан на корневой ФС, но отдельный диск не смонтирован, второй вызов может ошибочно принять корневую ФС за посторонний диск. Подтверждено на рабочем Linux-госте без изменений: для /tmp `findmnt --target` возвращает /dev/vda1 (/) и код 0, а `findmnt --mountpoint` не находит монтирования. Для реально смонтированного /mnt/lima-colima обе команды возвращают /dev/vdb1.

Кандидат исправления — заменить `--target` на `--mountpoint` в обеих проверках, сохранив проверку источника в первой. Проверить и отдельную ошибку resize2fs после штатного stop: исправление проверки само по себе ещё не доказывает чистое завершение гостя и корректное изменение размера ext4. Для production необходим fail-closed контроль: не запускать Docker при отсутствии правильного persistent data disk; проверить несколько циклов stop/start, сохранность данных и состояние cloud-init. Проверять отдельную сборку Colima на копии диска; рабочий VZ не изменять до подтверждения результата.

## Исправления и повторный тест (27.11.2026, 10:47–11:08 МСК)

- Отдельно собраны Colima 0.10.2-krunkit-fix.2 и Lima v2.1.2 с локальным исправлением. Исходные теги, патчи, проверка сборки, wrapper и сценарии миграции/проверки разрешения сохранены в `macos/colima-krunkit/`. Homebrew Lima, Colima, Tailscale, Amnezia не заменялись.
- Исправлена семантика findmnt --mountpoint, VirtioFS для Krunkit, защита systemd Docker/containerd и bind mount по точной метке диска/подкаталогу. При штатном stop Colima останавливает runtime, выполняет sync и чисто размонтирует bind mounts и persistent disk до SIGTERM Krunkit.
- Обнаружена вторая причина в Lima 2.1.2: cidata ошибочно вычисляла vdb для первого дополнительного диска, хотя Krunkit подключает root как vda, ISO как vdb и data disk как vdc. Исправлен расчёт только для Krunkit; тесты VZ, QEMU и Krunkit прошли. До исправления Lima Colima уже восстановила данные и прошла три stop/start, однако cloud-final оставался failed; после исправления Lima два полных цикла изолированной VM прошли с docker/containerd/cloud-final=active, UUID 0eb7dd38-5cad-4a0d-a26b-d88c29cc7c3b, всеми исходными контейнерами, volumes и образами. Негативный тест защиты на отсутствующем Docker bind mount успешно отказал. Штатное размонтирование зафиксировано.
- Рабочий диск повторно клонирован после штатной остановки VZ; production-кандидат использует проверенный root с защитой и свежую копию реального data disk. Автозапуск не дошёл до загрузки VM: macOS TCC отказала выполнению программы непосредственно с внешнего SSD (Operation not permitted). Исполняемые файлы размещены в небольшом локальном префиксе `~/Library/Application Support/FlyTerminal/colima-krunkit`; штатный TCC запрос для colima-fixed-v2 на Removable Volumes блокирует запуск до подтверждения пользователя. TCC не изменялся. Весь root/data и исходники сборки остаются на внешнем SSD.
- Сценарий отката восстановил исходные VZ root/data/config; новый кандидат сохранён отдельно (`failed-fixed-krunkit-20261127-110220`), ничего не удалено. При возврате Homebrew LaunchAgent также застрял в TCC; рабочий VZ запущен из уже авторизованного сеанса. Не считать production-миграцию завершённой. Перед новым окном обслуживания обязательна безостановочная проверка `permission-check.sh`: пользователь подтверждает штатный запрос macOS, статус из launchd должен вернуть 0. После этого `cutover.sh` проверит результат preflight до остановки VZ.

## Порядок проверки (окно обслуживания)

1. Согласовать краткий перерыв fallback Chromium и Quasar Bridge. Не запускать вторую VM на перегруженном хосте одновременно с рабочей. Не выполнять обновление Lima, если оно затрагивает Tailscale.
2. Проверить план установки и версии зависимостей krunkit/libkrun. Устанавливать только при наличии запаса ресурсов и подтверждённой версии с free page reporting. Не выполнять широкое обновление Homebrew.
3. После штатной остановки рабочей Colima создать отдельную согласованную резервную копию конфигурации и data disk на внешнем SSD; проверить её наличие, размер и возможность восстановления. Не копировать работающий data disk как консистентный бэкап.
4. Создать отдельный тестовый профиль с `--activate=false`, без общих каталогов хоста, без рабочих контейнеров и публикации их портов. Проверить запуск/остановку и Docker. При ошибках завершить тестовый профиль и запустить исходный без изменений.
5. Проверить возврат памяти: замеры macOS `memory_pressure`, `vm_stat`, `sysctl vm.swapusage` и гостя `/proc/meminfo` на покое, под ограниченной тестовой нагрузкой и после её освобождения. Рост доступной памяти после освобождения — критерий успеха; RSS процесса гипервизора не является достаточным показателем. Нагрузку повышать только при запасе RAM и остановить при росте давления/свопа. Не использовать нулевые страницы как единственный тест.
6. Перед миграцией проверить монтирование хостовых каталогов, доступ к Docker socket, форвардинг портов, restart policies и данные контейнеров. Krunkit не обеспечивает read-only для VirtioFS на уровне гипервизора; ограничить набор монтируемых каталогов и проверить, что требуемые свойства безопасности сохранены.
7. Только после всех проверок выбрать способ переноса с сохранением имени профиля default и Docker context colima. Colima поддерживает soft delete без `--data` и восстановление Docker data disk, но это не заменяет проверенную резервную копию и не должно быть первым шагом. Сохранить оригинальный VZ-профиль/диск для отката.
8. Проверить fallback Chromium (порт 7690, профиль браузера, сессии, загрузки и файловый обмен), Quasar Bridge (порт 8443, bind mounts), Gateway, Docker context и автозапуск. При любом регрессе вернуть исходный VZ-профиль. Не удалять резервную копию до завершения наблюдения.

## Критерии завершения

- рабочие Docker-контейнеры и volumes сохранены;
- Gateway, Chromium, Quasar Bridge и автозапуск успешно проверены;
- Tailscale и Amnezia не изменены;
- подтверждён возврат RAM хосту воспроизводимым замером после нагрузки;
- документирован способ отката, исходные данные сохранены.

До достижения этих критериев миграция не считается завершённой.
