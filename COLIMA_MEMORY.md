## Выбор технологии

VZ не гарантирует возврат страниц Linux в общее распоряжение macOS. Krunkit/libkrun >= 1.19.0 реализует free page reporting, но драйвер Lima остаётся экспериментальным. Фиксированный параметр memory остаётся верхней границей гостя; освобождаемые страницы могут повторно использоваться хостом.

**Решение:** VZ остаётся рабочим backend. Krunkit показал желаемый возврат памяти, но в текущей комбинации версий непригоден для production с постоянным data disk. Следующая попытка только после исправления #1614 либо отдельного воспроизводимого теста официального исправления с сохранённым диском, несколькими штатными перезапусками и проверкой всей цепочки до Docker. При разработке исправления использовать исключительно копию диска, не рабочий диск.

### Уточнение причины (27.11.2026)

В исходном коде Colima v0.10.2, `environment/vm/lima/disk.sh`, при проверке диска оба вызова `findmnt` используют `--target "$MOUNT_POINT"`. Это ищет файловую систему, содержащую путь, а не только точку монтирования. Если каталог уже создан на корневой ФС, но отдельный диск не смонтирован, второй вызов может ошибочно принять корневую ФС за посторонний диск. Подтверждено на рабочем Linux-госте без изменений: для /tmp `findmnt --target` возвращает /dev/vda1 (/) и код 0, а `findmnt --mountpoint` не находит монтирования. Для реально смонтированного /mnt/lima-colima обе команды возвращают /dev/vdb1.

Кандидат исправления — заменить `--target` на `--mountpoint` в обеих проверках, сохранив проверку источника в первой. Проверить и отдельную ошибку resize2fs после штатного stop: исправление проверки само по себе ещё не доказывает чистое завершение гостя и корректное изменение размера ext4. Для production необходим fail-closed контроль: не запускать Docker при отсутствии правильного persistent data disk; проверить несколько циклов stop/start, сохранность данных и состояние cloud-init. Проверять отдельную сборку Colima на копии диска; рабочий VZ не изменять до подтверждения результата.

## Порядок проверки (окно обслуживания)

1. Согласовать краткий перерыв fallback Chromium и Quasar Bridge. Не запускать вторую VM на перегруженном хосте одновременно с рабочей. Не выполнять обновление Lima, если оно затрагивает Tailscale.
2. Проверить план установки и версии зависимостей krunkit/libkrun. Устанавливать только при наличии запаса ресурсов и подтверждённой версии с free page reporting. Не выполнять широкое обновление Homebrew.
3. После штатной остановки рабочей Colima создать отдельную согласованную резервную копию конфигурации и data disk на внешнем SSD; проверить её наличие, размер и возможность восстановления. Не копировать работающий data disk как консистентный бэкап.
4. Создать отдельный тестовый профиль с `--activate=false`, без общих каталогов хоста, без рабочих контейнеров и публикации их портов. Проверить запуск/остановку и Docker. При ошибках завершить тестовый профиль и запустить исходный без изменений.
5. Проверить возврат памяти: замеры macOS `memory_pressure`, `vm_stat`, `sysctl vm.swapusage` и гостя `/proc/meminfo` на покое, под ограниченной тестовой нагрузкой и после её освобождения. Рост доступной памяти после освобождения — критерий успеха; RSS процесса гипервизора не является достаточным показателем. Нагрузку повышать только при запасе RAM и остановить при росте давления/свопа. Не использовать нулевые страницы как единственный тест.
6. Перед миграцией проверить монтирование хостовых каталогов, доступ к Docker socket, форвардинг портов, restart policies и данные контейнеров. Krunkit не обеспечивает read-only для VirtioFS на уровне гипервизора; ограничить набор монтируемых каталогов и проверить, что требуемые свойства безопасности сохранены.
7. Только после всех проверок выбрать способ переноса с сохранением имени профиля default и Docker context colima. Colima поддерживает soft delete без `--data` и восстановление Docker data disk, но это не заменяет проверенную резервную копию и не должно быть первым шагом. Сохранить оригинальный VZ-профиль/диск для отката.
8. Проверить fallback Chromium (порт 7690, профиль браузера, сессии, загрузки и файловый обмен), Quasar Bridge (порт 8443, bind mounts), Gateway, Docker context и автозапуск. При любом регрессе вернуть исходный VZ-профиль. Не удалять резервную копию до завершения наблюдения.

- рабочие Docker-контейнеры и volumes сохранены;
